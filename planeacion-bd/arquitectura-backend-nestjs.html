01

Arquitectura Hexagonal — Las 3 Capas

⬡
Principio central El dominio no sabe que existe NestJS, HTTP, Postgres ni ningún PAC. Solo entiende entidades, puertos e interfaces. Todo lo externo es un adaptador enchufable.
HEXAGONAL ARCHITECTURE — REQUEST FLOW
🌐 Infrastructure (Adapters IN) HTTP Controllers, Guards, Interceptors, Pipes de validación, WebSocket Gateway
NestJS Controllers class-validator
↓
⚙️ Application Layer (Use Cases) EmitirFacturaUseCase, CancelarCFDIUseCase, ValidarTicketUseCase — orquestan el dominio
Commands Queries DTOs
↓
🏛️ Domain Layer (Core) Entities (CFDI, Ticket, Empresa), Value Objects (RFC, Moneda), Domain Events, Ports
Puro TypeScript Sin frameworks
↓
🔌 Infrastructure (Adapters OUT) Postgres (TypeORM), Redis (BullMQ), PAC Adapter (Facturama), S3/R2, Mail, Logger
TypeORM BullMQ Axios
⚠
Regla de dependencias Las flechas SOLO apuntan hacia adentro. El dominio no importa nada de capas externas. Si necesitas cambiar el PAC de Facturama a SW2, solo cambias el adaptador — el dominio no se toca.

04

Flujo Crítico: Emisión de Factura

1
Request ingresa al Controller
Guard JWT verifica token. Throttler limita 10 req/min por IP. Pipe valida DTO con class-validator.
POST /api/v1/cfdi/emitir Authorization: Bearer <jwt> Body: EmitirCfdiDto { ticket_id, receptor, ... }
2
ValidarTicketUseCase
Verifica que el ticket exista en BD. Verifica que su estado sea PENDIENTE. Si ya está FACTURADO → lanza TicketAlreadyBilledException (409).
// Si ticket no existe → 404 // Si ticket.estado === 'FACTURADO' → 409 Conflict // Si ticket.estado === 'CANCELADO' → 422
3
Distributed Lock (Redis)
Adquiere lock con clave lock:ticket:{id} con TTL 30s usando Redlock. Si el lock falla → 429 con mensaje "Factura en proceso". Evita doble-timbrado por concurrencia.
SET lock:ticket:ABC123 owner NX EX 30
4
Crear CFDI en BD (estado: PENDIENTE_TIMBRADO)
Genera UUID interno del CFDI. Guarda el borrador en BD con estado PENDIENTE_TIMBRADO antes de encolar. Actualiza ticket a EN_PROCESO.
cfdi.uuid_interno = uuidv4() cfdi.estado = 'PENDIENTE_TIMBRADO' ticket.estado = 'EN_PROCESO'
5
Encolar trabajo en BullMQ
El controller retorna 202 Accepted inmediatamente con el UUID del CFDI. El worker de timbrado toma el job de forma async.
queue.add('timbrar', { cfdi_id }, { attempts: 3, backoff: { type: 'exponential', delay: 2000 } }) → return { status: 202, cfdi_id }
6
Worker: Firma y Timbrado
Consulta primero al PAC si ya existe timbre para ese UUID interno (idempotencia). Si existe, usa el timbre existente. Si no, genera XML, firma con CSD, envía al PAC.
const existing = await pac.consultarPorFolioInterno(uuid_interno) if (existing) return guardarTimbre(existing) // Si no existe: generar → firmar → timbrar
7
Finalización
Guarda XML timbrado en R2. Actualiza CFDI a TIMBRADO con UUID SAT. Actualiza ticket a FACTURADO. Libera lock. Encola notificación por email. Emite domain event.

// Estados del CFDI

STATE MACHINE
BORRADOR Antes de encolar
↓
PENDIENTE_TIMBRADO En cola, esperando worker
↓
EN_TIMBRADO Worker procesando, lock activo
↓    ↘ error

ERROR_TIMBRADO Falló tras 3 intentos, requiere revisión
↓ (si aplica)

↓

↓

05

Idempotencia y Protección Doble-Timbrado

🚨
El peor escenario posible El PAC timbra el CFDI pero la respuesta se pierde por timeout de red. El worker reintenta, el PAC timbra de nuevo → dos CFDIs con el mismo contenido en el SAT. Esto es un problema fiscal real.

// Las 3 capas de protección

Capa Mecanismo Qué previene Dónde vive
1 — DB State CHECK ticket.estado = 'PENDIENTE' Solicitudes duplicadas por el usuario ValidarTicketUseCase
2 — Redis Lock Redlock con TTL 30s Concurrencia (dos requests al mismo tiempo) Controller / Use Case
3 — PAC Query Consultar folio interno ANTES de timbrar Reintento de worker tras timeout de red TimbradoWorker
// workers/timbrado.worker.ts — lógica anti-duplicado async process(job: Job<TimbradoJobDto>) { const cfdi = await this.cfdiRepo.findById(job.data.cfdi_id); // Capa 3: consultar PAC antes de timbrar const existing = await this.pac.consultarPorFolioInterno(cfdi.uuid_interno); if (existing) { // Ya fue timbrado, solo guarda el timbre y termina return this.guardarTimbreExistente(cfdi, existing); } // Si no existe: firmar y timbrar const xml = await this.xmlBuilder.construir(cfdi); const xmlFirmado = await this.csdService.firmar(xml); // en memoria const timbre = await this.pac.timbrar(xmlFirmado); await this.cfdiRepo.marcarTimbrado(cfdi.id, timbre); await this.ticketRepo.marcarFacturado(cfdi.ticket_id); await this.storage.guardarXml(timbre.xml, cfdi.uuid_sat); await this.notifQueue.add('email', { cfdi_id: cfdi.id }); }

06

Arquitectura de Colas (BullMQ)

⚡
timbrado-queue
  • Concurrency: 3 workers
  • Attempts: 3 reintentos
  • Backoff: exponential (2s, 4s, 8s)
  • Priority por plan del cliente
  • Job timeout: 60s
🔄
cancelacion-queue
  • Concurrency: 2 workers
  • Attempts: 5 (SAT puede tardar)
  • Backoff: exponential (5s base)
  • Polling de estado cada 5 min
  • Job delay configurable
📧
notificaciones-queue
  • Concurrency: 5 workers
  • Attempts: 3
  • Backoff: fixed (30s)
  • No bloquea el timbrado
  • Log de éxito/fallo por envío
🗑️
cleanup-queue (cron)
  • Limpia jobs completados (+7 días)
  • Purga sesiones expiradas
  • Refresca cache de catálogos SAT
  • Corre cada 24h (schedulado)
💡
Bull Board (panel de monitoreo) Instala @bull-board/api para tener un panel visual de todas las colas, jobs en progreso, fallidos y completados. Solo accesible desde la IP del admin o con autenticación separada.

07

Seguridad — Capas Completas

Capa 1 — Red
Perímetro y TLS
  • TLS 1.3 obligatorio (no TLS 1.2)
  • HSTS con preload
  • Certificado Let's Encrypt auto-renovado
  • Nginx como reverse proxy (NestJS no expuesto directamente)
  • Firewall: solo 443 y 22 abiertos
Capa 2 — HTTP
Headers y CORS
  • Helmet.js: CSP, X-Frame-Options, HSTS
  • CORS whitelist solo dominios del cliente
  • Content-Type validation en todas las rutas
  • No exponer stack traces en respuestas
  • Request ID header para trazabilidad
Capa 3 — Autenticación
JWT + Refresh
  • Access token: 15 min TTL
  • Refresh token: 7 días, rotación en cada uso
  • Blacklist de tokens revocados en Redis
  • Algoritmo RS256 (no HS256)
  • Logout invalida ambos tokens
Capa 4 — Autorización
RBAC + Tenant
  • Roles: ADMIN, OPERADOR, VIEWER
  • Guard verifica rol en cada endpoint
  • Toda query filtra por empresa_id del token
  • No existe endpoint sin autenticación (excepto /auth/login)
  • Decorador @Roles para control granular
Capa 5 — Datos
Cifrado en Reposo
  • CSD cifrados con AES-256-GCM
  • Contraseñas con bcrypt (cost 12)
  • Datos fiscales sensibles cifrados en BD
  • Backups de BD también cifrados
  • Variable de entorno con master key nunca en repositorio
Capa 6 — Aplicación
Validación y Sanitización
  • class-validator en todos los DTOs
  • No se usa eval() ni Function()
  • Parameterized queries (TypeORM previene SQL injection)
  • Sanitizar inputs antes de XML (evitar XXE)
  • Validar RFC con regex + schema SAT

// Aislamiento de CSD — Regla crítica

// shared/crypto/csd.service.ts // Los certificados NUNCA salen de este servicio descifrados @Injectable() export class CsdService { // Solo este método accede a la tabla 'csd_certificados' async firmar(xmlCadena: string, empresaId: string): Promise<string> { const csdCifrado = await this.csdRepo.findByEmpresa(empresaId); // Descifrar EN MEMORIA con master key de variable de entorno const csdBuffer = decrypt(csdCifrado.llave, process.env.MASTER_KEY); // Firmar y limpiar la memoria inmediatamente const firma = rsaSign(xmlCadena, csdBuffer); csdBuffer.fill(0); // zero out buffer await this.auditLog.registrar({ accion: 'CSD_USADO', empresaId }); return firma; } // Ningún otro método, ningún getter que exponga el CSD descifrado }

Protección DDoS y Rate Limiting

Endpoint / Grupo Límite Ventana Mecansmo
POST /auth/login 5 intentos 15 min por IP Throttler + bloqueo temporal IP
POST /cfdi/emitir 30 req/min por usuario @Throttle() personalizado
GET /catalogos/* 100 req/min por usuario Cache Redis previene BD hits
Todos los endpoints (global) 200 req/min por IP ThrottlerGuard global en AppModule
Nivel Nginx 50 conn simultáneas por IP limit_conn + limit_req en Nginx

// NestJS ThrottlerModule

// app.module.ts ThrottlerModule.forRoot({ throttlers: [ { name: 'short', ttl: 1000, limit: 5 }, { name: 'medium', ttl: 10000, limit: 20 }, { name: 'long', ttl: 60000, limit: 100 } ], storage: new ThrottlerStorageRedisService(redis) }) // Uso en controller específico: @Throttle({ short: { ttl: 60000, limit: 5 } }) @Post('login') async login() { ... }

// Nginx rate limiting

# /etc/nginx/nginx.conf limit_req_zone $binary_remote_addr zone=api:10m rate=50r/m; limit_conn_zone $binary_remote_addr zone=conn:10m; server { location /api/ { limit_req zone=api burst=20 nodelay; limit_conn conn 20; limit_req_status 429; proxy_pass http://localhost:3000; } }
🛡️
Protección multicapa: si un atacante pasa el Nginx, lo para el ThrottlerGuard. Si pasa el ThrottlerGuard, la lógica de negocio aún valida tickets y estados. Para DDoS volumétrico real (+ de 10k req/s), usa Cloudflare Free plan delante del VPS — absorbe la carga antes de que llegue a tu servidor.

Health Checks y Graceful Shutdown

// HealthModule con @nestjs/terminus

// modules/health/health.controller.ts @Controller('health') export class HealthController { constructor( private health: HealthCheckService, private db: TypeOrmHealthIndicator, private redis: RedisHealthIndicator, private http: HttpHealthIndicator, ) {} // Liveness: ¿está vivo el proceso? @Get('live') async liveness() { return { status: 'ok' }; // siempre 200 si el proceso existe } // Readiness: ¿puede recibir tráfico? @Get('ready') @HealthCheck() async readiness() { return this.health.check([ () => this.db.pingCheck('postgres'), () => this.redis.checkHealth('redis', { type: 'redis' }), ]); } // Deep health: para panel interno @Get('deep') @UseGuards(JwtAuthGuard) // ← protegido, solo admins @HealthCheck() async deep() { return this.health.check([ () => this.db.pingCheck('postgres'), () => this.redis.checkHealth('redis', { type: 'redis' }), () => this.http.pingCheck('pac', process.env.PAC_API_URL), ]); } }

// Graceful Shutdown en main.ts

// main.ts async function bootstrap() { const app = await NestFactory.create(AppModule); // Habilitar shutdown hooks de NestJS app.enableShutdownHooks(); await app.listen(3000); } // En cada módulo con conexiones externas: @Injectable() export class TimbradoWorker implements OnApplicationShutdown { async onApplicationShutdown(signal: string) { // Esperar que el job actual termine // antes de que el proceso muera await this.worker.close(); } }
SHUTDOWN SEQUENCE
1. SIGTERM recibido Docker / sistema operativo envía señal
↓
2. Dejar de aceptar requests Nginx deja de routear al proceso
↓
3. Esperar jobs en curso BullMQ worker termina el job actual (max 30s)
↓
4. Cerrar conexiones TypeORM pool, Redis client, HTTP connections
↓
5. Proceso termina con exit 0 Sin datos corruptos, sin jobs huérfanos
⚠
Sin graceful shutdown Si el proceso muere mientras timbra, el job queda en estado active en BullMQ y no se reintenta automáticamente. Con graceful shutdown, BullMQ lo marca como stalled y lo reintenta solo.

// Interceptor de Request ID

// shared/interceptors/request-id.interceptor.ts // Propaga el mismo ID por toda la cadena de llamadas @Injectable() export class RequestIdInterceptor implements NestInterceptor { intercept(ctx: ExecutionContext, next: CallHandler) { const req = ctx.switchToHttp().getRequest(); req.id = req.headers['x-request-id'] ?? uuidv4(); return next.handle().pipe( tap(() => { const res = ctx.switchToHttp().getResponse(); res.setHeader('x-request-id', req.id); }) ); } }

⚠

// Flujo de cancelación con polling // 1. Solicitar cancelación al PAC const res = await pac.solicitarCancelacion({ uuid_sat, rfc_emisor, motivo: '01', uuid_sustitucion }); // 2. El PAC responde con uno de: // 201 → Cancelado directamente (montos <$1000 o mismo RFC) // 202 → Cancelación pendiente de aceptación // 203 → Plazo vencido, cancelado automáticamente if (res.estatus === '202') { cfdi.estado = 'CANCELACION_PENDIENTE'; cfdi.cancelacion_solicitada_at = new Date(); await cfdiRepo.save(cfdi); // Encolar job de polling cada 4 horas await cancelacionQueue.add( 'verificar-cancelacion', { cfdi_id: cfdi.id }, { repeat: { every: 4 * 60 * 60 * 1000 }, jobId: cfdi.id } ); } // workers/cancelacion.worker.ts async verificarCancelacion(job: Job) { const cfdi = await cfdiRepo.findById(job.data.cfdi_id); const estado = await pac.consultarEstatusCancelacion(cfdi.uuid_sat); if (estado === 'CANCELADO') { cfdi.estado = 'CANCELADO'; await cfdiRepo.save(cfdi); await cancelacionQueue.removeRepeatable(cfdi.id); await notifQueue.add('cfdi-cancelado', { cfdi_id: cfdi.id }); } // Si lleva +72h y sigue pendiente → cancelado automático por SAT }

// Búsqueda y paginación de CFDIs

// GET /cfdi?page=1&limit=20&estado=TIMBRADO&rfc=RFC123 async buscarCfdis(filtros: BuscarCfdiDto) { const qb = this.cfdiRepo.createQueryBuilder('c') .leftJoinAndSelect('c.ticket', 't') .orderBy('c.created_at', 'DESC'); if (filtros.estado) qb.andWhere('c.estado = :estado', { estado: filtros.estado }); if (filtros.rfc) qb.andWhere('c.receptor_rfc ILIKE :rfc', { rfc: `%${filtros.rfc}%` }); if (filtros.fecha_desde) qb.andWhere('c.created_at >= :desde', { desde: filtros.fecha_desde }); if (filtros.fecha_hasta) qb.andWhere('c.created_at <= :hasta', { hasta: filtros.fecha_hasta }); if (filtros.folio) qb.andWhere('t.folio = :folio', { folio: filtros.folio }); const [items, total] = await qb .skip((filtros.page - 1) * filtros.limit) .take(filtros.limit) .getManyAndCount(); return { data: items, meta: { total, page: filtros.page, limit: filtros.limit, pages: Math.ceil(total / filtros.limit) } }; }

// Retención de documentos — Artículo 30 CFF

⚖️
Obligación legal: 5 años mínimo (en la práctica, guarda 10) El Código Fiscal de la Federación (Art. 30) obliga a conservar la contabilidad — incluyendo CFDIs — por un mínimo de 5 años. Si el SAT audita a tu cliente y los documentos no están, la responsabilidad recae sobre él. Tu sistema es quien los custodia.

// Estrategia de retención en R2/S3

// Estructura de paths en R2 — pensada para retención y auditoría xmls/{empresa_id}/{año}/{mes}/{uuid_sat}.xml pdfs/{empresa_id}/{año}/{mes}/{uuid_sat}.pdf reportes/{empresa_id}/{año}/{nombre_reporte}.csv backups/{empresa_id}/{año}/{mes}/db_{fecha}.sql.gz // En Cloudflare R2, configurar Object Lifecycle Rule: // - xmls/ y pdfs/ → NO expirar nunca (o 10 años) // - reportes/ → expirar en 90 días // - backups/ → expirar en 365 días // En BD: columna que marca si el CFDI fue "archivado" ALTER TABLE cfdis ADD COLUMN archivado_at TIMESTAMPTZ; -- cuando se movió a cold storage // Cron anual: marcar como archivado los CFDIs con +1 año @Cron('0 3 1 1 *') // 1 enero a las 3am async archivarCfdisViejos() { await cfdiRepo.query(` UPDATE cfdis SET archivado_at = NOW() WHERE created_at < NOW() - INTERVAL '1 year' AND archivado_at IS NULL `); }
